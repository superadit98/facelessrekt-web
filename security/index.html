Security Research

Web application security · independent research

I break web applications the way real attackers do: not by finding a scary string, but by proving that one account can reach another account's data, or that a business rule holds only in the UI. Everything below was reported privately to the vendor before it appeared here.

Focus areas

ClassWhat I test
Broken access control Missing server-side authorisation, privilege escalation, role confusion, horizontal and vertical boundaries
IDOR Direct object references across tenants and users; sequentially-guessable identifiers; UUIDs leaked in responses, exports or emails
PII exposure Personal data reachable without authorisation — through APIs, exports, cached pages, logs or misconfigured storage
Delivery-order / fulfilment abuse Address and recipient manipulation, re-routing after payment, carrier and status field tampering, order replay
Business logic Race conditions, negative and fractional quantities, coupon and credit replay, price tampering, state-machine shortcuts
Authentication & session Password reset flows, token lifetime, session fixation, MFA bypass, account enumeration

Severity

Severity follows impact, not novelty. A dull bug that exposes other people's personal data outranks a clever one that only prints a debug string.

LevelTypical impact
criticalMass PII exposure, authentication bypass, full account takeover, remote code execution
highCross-tenant data access, single-account takeover, privileged action as another user, order or payment manipulation
mediumLimited data exposure, stored logic abuse with financial impact, SSRF to internal services, CSRF on a sensitive action
lowInformation disclosure with no personal data, missing hardening, reflected-only issues

Disclosure policy

  • Report privately to the vendor or program first. No public details before a fix.
  • Coordinated disclosure: 90 days is the default window, extendable when the vendor is actively working on it.
  • No exploitation beyond what is needed to prove impact. No bulk data retrieval — a single record is enough to demonstrate exposure, and I stop there.
  • Personal data encountered during testing is never stored, shared or retained. It is reported by type and count, not by content.
  • No persistence, no lateral movement, no denial of service, no social engineering of staff.
  • Findings are published only after remediation, or with explicit written permission, and always redacted.
  • If a vendor is unresponsive, escalation goes through the program or CERT, not through a public drop.
